# 성능 · 사용성 · 확장성 측정 기록

요구사항 PERFORMANCE-001·002, USABILITY-001·002, SCALABILITY-002 를 실제로 재 본 값이다.
측정 조건을 같이 적는다 — 조건이 다르면 숫자를 비교하지 않는다. (2026-09-28 · Claude)

## PERFORMANCE-001 화면 응답 성능

**조건** 운영 사이트(https://fee-di-t-frontend.vercel.app), 사용자 Chrome, 운영 계정 로그인 상태.
측정 중 Chrome 창이 화면에 보이지 않는 상태(visibilityState=hidden)였다 — 이때 브라우저가 그리기(paint)와
타이머를 늦추므로 **FCP · LCP 는 기록되지 않았고**, 타이머를 거치는 측정(지표 화면 전체 렌더)은 1초 단위로 뭉개져 쓰지 않았다.
아래는 그 영향을 받지 않는 값만이다.

| 목표 | 측정 | 값 | 판정 |
|---|---|---|---|
| 첫 진입 3초 | Navigation Timing `loadEventEnd` | 세션 첫 진입 **1.11초**(DOMContentLoaded 0.85초, TTFB 73ms) · 다시 들어올 때 0.24초 | 충족 |
| 탭 전환 0.5초 | 상단 탭 클릭 → 새 화면 표시 + 레이아웃까지(5개 화면 × 3회) | **2 ~ 25ms** | 충족 (그리기 시간 제외) |
| 지표 화면 렌더 1초 | 지표 API(`/api/trend`) 응답 — 화면이 기다리는 부분 | 버셀 캐시 적중 21ms · 미적중 7건 **0.49 ~ 1.04초(중앙값 0.68초)** | 대체로 충족, 캐시 미적중 1건이 1초를 넘음 |
| 자동완성 300ms | 검색창 입력 → 후보 목록 갱신(8개 단어) | **3 ~ 7ms** (사전을 미리 받아 브라우저에서 거른다) | 충족 |

남은 것: 창이 보이는 상태에서 FCP · LCP 와 '지표 화면 첫 그림까지' 를 다시 잰다.
캐시 미적중 때 지표 API 가 0.7초 안팎이라, 1초 목표를 안정적으로 지키려면 API 응답을 줄여야 한다.

## PERFORMANCE-002 모션 프레임 유지

**조건** 이 저장소의 빌드(`vite preview`)를 **GPU 없는 헤드리스 Chromium**(CPU 2개)에서 `requestAnimationFrame` 간격으로 측정.
실제 기기보다 느린 환경이라 참고값이다. 드롭 = 한 프레임이 25ms(16.7ms × 1.5) 넘게 걸린 비율.

| 장면 | fps | 드롭 |
|---|---|---|
| 인트로 로딩 애니메이션(4초) | 60 | 0% |
| 스타일 화면 스크롤 | 55 | 7% |
| 홈으로 전환 | 54 | 10% |
| 스타일 · 살!말? 으로 전환 | 40 ~ 44 | 26 ~ 34% |
| 트렌드 분석으로 전환 | 17 | 92% |

인트로 · 스크롤은 목표(60fps, 드롭 5% 이하)에 가깝고, **화면 전환 — 특히 트렌드 분석 진입 — 은 프레임이 떨어진다.**
실제 기기(맥북 · 폰)에서 Chrome 성능 기록으로 다시 재야 판정할 수 있다.

## USABILITY-001 반응형

**조건** 로컬 빌드, 390 · 768 · 1280px, 홈 · 트렌드 · 살!말? · 스타일 · 요금제 · 로그인 · 회원가입 7개 화면(로그인 전).
가로 넘침(`scrollWidth > clientWidth`) **21개 조합 모두 없음.**
920px 이하에서 트렌드 사이드바는 접힌 채 시작하고, 펼쳐도 본문을 밀지 않으며, 메뉴를 고르면 접힌다(`responsive.css` · `router.js`).
로그인 후 화면(내 피드 · 금주의 리포트 등)은 360 · 390 · 768 · 1440px 로 따로 확인했다(DEVELOPLOG 2026-09-28 01:52).

## USABILITY-002 접근성

- **모션 최소화**: `prefers-reduced-motion` 에서 애니메이션을 멈춘다.
- **명도 대비**: axe-core(WCAG 2 A · AA) 점검에서 본문 · 보조 글자 · 버튼은 통과. **남은 것은 큰 제목 속 브랜드 코랄 강조 글자 3곳**
  (홈 '트렌드', 트렌드 분석 제목의 강조어, 살!말? '말까')뿐이다 — #ff6b4a 는 지면 위 2.45:1 로 큰 글자 기준(3:1)에도 못 미친다.
  브랜드 색을 바꾸는 일이라 디자인 결정이 필요하다.
- **키보드**: 모든 화면에서 Tab 으로 상단 메뉴 · 버튼 · 입력칸 · 카드에 닿고, 초점에 코랄 테두리(`:focus-visible`)가 보인다.
  본문 모드에서 보이지 않는 인트로 버튼으로 초점이 들어가던 것을 막았다. 닫힌 세부 검색 팝업으로 초점이 들어가던 것도 막았다.
- 스크린리더 전체 점검은 하지 않았다.

## SCALABILITY-002 지표 산출 배치 확장

**조건** 로컬 Postgres 16, CPU 2개 · 메모리 7GB. 합성 데이터 — 사전 용어 **1만 개**, 텍스트 문서 12.4만 건,
용어 언급 37.2만 건(35일). 매일 04:10 배치의 지표 재계산 단계(`rebuild_text_metrics`, 최근 35일)를 그대로 돌렸다.

| 항목 | 값 |
|---|---|
| 소요 시간 | **123초** (목표 6시간) |
| 만든 행 | 용어 일별 지표 306,362 · 연관어 413,795 · 플랫폼 105 |
| 최대 메모리 | **3.6GB** |

지표 계산은 6시간 목표 안에 넉넉히 끝난다. 다만 **메모리를 3.6GB 까지 쓴다** — 운영 워커 서버 메모리가 이보다 작으면
용어가 1만 개로 늘 때 워커가 죽을 수 있다. 같은 배치의 LLM 텍스트 분석 단계는 하루 300건 상한(`FEEDIT_TEXT_DAILY_ANALYSIS_LIMIT`)이
걸려 있고 외부 API 비용이 들어 부하 시험에 넣지 않았다.
