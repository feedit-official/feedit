### 조사에서 나온 것 — 원인

**1. 트렌드 온도의 가속 성분이 포화됐다.**

`metrics.py:56` 의 `momentum = 100/(1+exp(-6×(ma7/ma28-1)))` 이
2026-09-01 기준 451개 term 중 410개(90.9%)에서 99 이상으로 나온다.

원인은 공식이 아니라 **수집량이 계속 늘고 있다는 사실**이다.
6월 이후 일별 term 수가 계속 증가해 `ma7/ma28` 이 항상 1을 넘고,
`exp(-6x)` 가 금세 0으로 죽어 시그모이드가 천장에 붙는다.
8/31 백필 461건이 이걸 더 밀었다.

결과: `temp = 0.6×level + 0.4×momentum` 이 사실상 `0.6×level + 40` 이다.
**온도로는 "오르는 중 / 식는 중"을 구분할 수 없다.**

→ 챗봇은 방향을 `ma7/ma28` 배수로 직접 읽어 말한다. 온도를 근거로 쓰지 않는다.
→ 파이프라인 쪽 수정 제안은 설계서 9장.

**2. `Lexicon.extract(q, "free")` 는 브랜드를 한 개도 못 뽑는다.**

`lexicon.py:120~121` 이 `free` 표기 목록에서 brand 를 통째로 제외한다.
실제로 돌려서 센 값 — 전체 표기 6,573 중 free 는 1,058 (84% 제외), brand 표기 5,472 전부 제외.

거기에 `RISKY` 35개가 사전 표기와 겹쳐 같이 빠진다.
`클래식`(style) · `면`(코튼) · `백`(가방) 등.

원인은 `free` 가 **자유 글(댓글·블로그) 전용**으로 만들어졌기 때문이다.
챗봇 질문은 자유 글이 아니라 **사용자가 의도를 갖고 친 짧은 문장**이라 잣대가 달라야 한다.

→ 설계서 3.3 에 `mode="question"` 3단 추출을 제안했다.
   1단 `free` → 2단 어절 완전일치로 RISKY 복구 → 3단 어절 n-gram 으로 브랜드.
   과거 오탐은 전부 부분 문자열에서 나왔고, 어절 완전일치는 그 경로가 아니다.
   **아직 돌려 보지 않았다.** 검증 3종을 설계서에 적어 뒀다.

**3. 가격 이력이 2~3일뿐이라 `Δdisc_14` 를 계산할 수 없다.**

`product_stat` 의 `stat_date` distinct = 3, `product_price_snapshot` 최초 수집 2026-08-31.
지표계산 설계서 4장의 구매 점수는 14일 전 대비를 요구한다.

→ 살!말?지수의 값 축은 신뢰도 0.14~0.21 로 들어가 사실상 빠진다.
   지어내지 않고 "가격 이력이 부족하다"로 답한다.

**4. 구매의향 표본이 term 당 1~4건이다.**

`intent.py` 의 수축식 `S×n/(n+100)` 때문에 표본 4건이면 지수가 50에서 2점도 안 움직인다.

원인은 폴백 코드 한 줄이다.

```js
if(head) aiMsg.html=head;      // ← head 가 비면 목업이 안 지워진다
```

서버가 답하기 전에 목업 문장을 미리 채워 두는 구조인데(서버가 없어도 데모가 돌게 하려고),
거절 응답은 `head` 가 비어 있어 `if(head)` 가 거짓이 된다. 그래서 목업이 살아남았다.

정상 응답에서는 `head` 에 글자가 차므로 덮였다. **거절일 때만 새는 버그**라 스모크에서 안 걸렸다.

고친 방법 — `served` 플래그를 둬서 **서버가 답했으면 비어 있어도 덮는다.**

```js
if(served){ aiMsg.html=head; aiMsg.key=null; aiMsg.live=true; }
else if(head){ aiMsg.html=head; aiMsg.live=true; }
```

### 무엇을 왜 고쳤나

18:23 작업은 질문별로 같은 3탭을 반복하는 문제는 줄였지만, 결국 `ranking`·
`pulse`·`compare` 등 이름 붙은 완성 양식 중 하나를 고르는 구조였다. 요구사항은
양식 선택이 아니라, 데이터 조회를 끝낸 모델이 필요한 지표와 정보 관계를 판단한
뒤 그 결과에 맞는 화면을 매번 구성하는 스킬이었다. 앞선 구현은 그 요구를 충분히
반영하지 못했다.

`tools.py`에 `compose_report`를 추가했다. 오케스트레이터가 조회를 마친 뒤 실제로
받은 결과만 대상으로 모듈 종류, `hero/card/chart/list/editorial/compact` 표현 역할,
12열 캔버스 폭, 강조도, 색·표면·밀도를 정한다. 완성 양식 이름이나 HTML·CSS·수치·
상품은 이 도구의 인자가 아니다.

`report_designer.py`와 고정 plan 목록을 제거하고 `report_skill.py`를 추가했다.
`agent_blocks.py`가 실제 도구 결과로 콘텐츠 카탈로그를 만든 뒤, 스킬이 모델의 UI
스펙과 id/kind/term 이 일치하는 블록만 결합한다. 없는 모듈 요청은 버리고,
`declare_missing` 결과는 디자인에서 빼더라도 끝에 반드시 붙인다. 디자인 호출이
끊긴 경우에는 이름 붙은 양식을 선택하지 않고 실제 콘텐츠를 순서대로 흘리는
안전한 캔버스로 폴백한다.

프론트에는 `generative_report` 렌더러와 12열 캔버스를 추가했다. 모델이 HTML을
직접 보내지 않고 서버가 검증한 토큰만 조합하므로 질문마다 다른 화면을 만들면서도
스크립트 삽입과 임의 CSS 생성을 막는다. 이전 대화에 저장된 `reportset`은 다시
열 수 있도록 호환 렌더러만 남겼고, 새 응답 경로에서는 더 이상 사용하지 않는다.
