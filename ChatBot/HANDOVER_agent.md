앞으로 이 부분을 맡을 분에게. **읽는 순서대로** 썼다.
30분이면 지금 상태를 다 알 수 있게, 함정은 함정이라고 적어 뒀다.

**★ 고치기 전에 `ChatBot/AGENTS.md` 를 먼저 읽을 것** (2026-09-10 추가).
이 문서는 *무엇을 왜 고쳤는가*를, 그쪽은 *어떻게 고칠 것인가*를 담는다 —
특히 "증상을 덮지 말고 도구·스킬로 능력을 올린다" 는 규칙이 거기 있다.

`ChatBot/README.md` 는 여전히 유효하다 — 켜는 법, 크롤러 저장소가 왜 필요한지는
거기에 있다. 이 문서는 **README 가 아직 모르는 것**, 즉 새로 만든 에이전트 경로만 다룬다.

## 1. 한 줄 요약

챗봇 답변을 만드는 길이 지금 **두 개**다. 환경변수 하나로 갈아 낀다.

```bash
FEEDIT_CHAT_ORCHESTRATOR=1   # 새 경로 (도구 루프)
# 없거나 0                    # 기존 경로 (정규식 의도 분류 → 고정 템플릿)
```

기존 경로를 **지우지 않았다.** 새 경로가 어느 질문에서 더 나은지 실제로 재 본 뒤에
기본값을 바꾸면 된다. 돌고 있는 챗봇을 세우지 않고 갈아 끼우기 위한 것이다.

---

## 2. 왜 새로 만들었나

기존 경로는 `intents.py` 의 정규식 14개로 의도를 **확정**하고, `templates.py` 가
그 의도에 붙은 블록을 그렸다. 근거를 보기 전에 되돌릴 수 없는 결정을 하는 구조라
세 곳에서 깨진다.

| 깨지는 질문 | 왜 |
| --- | --- |
| "살로몬 XT-6 지금 사도 돼?" | 할인률·수명주기·리세일 셋 다인데 하나를 고르는 순간 나머지 근거가 사라진다 |
| "이거 어때?" | 분류하려면 "이거" 가 뭔지 알아야 하는데, 그건 분류 이후에나 정해진다. 순서가 뒤집혀 있다 |
| "요즘 뭐가 핫해?" | 사전에 걸리는 말이 없다고 범용으로 흘러갔다. 답이 용어인 질문인데 우리 데이터를 안 보고 지어냈다 |

새 경로는 의도 코드를 만들지 않는다. **다음에 부를 도구**만 정하고, 결과를 보고
다시 정한다. 위 셋이 전부 이 한 가지로 풀린다.

> 설계 원칙: **분류하지 말고 도구를 골라라.**
> 어휘 사전은 관문(gate)이 아니라 도구다. 되묻기(`ask_user`)와 없다고 말하기
> (`declare_missing`)도 실패 경로가 아니라 도구다.

## 4. 손대기 전에 알아야 할 함정

### ★ 값은 도구에서만 나온다

제일 위험한 실패는 **"DB 가 안 붙었는데 화면에 그럴듯한 숫자가 떠 있는 것"** 이다.
화면 쪽은 이미 그 원칙을 지킨다 — 값이 없으면 `unavailableHTML` 이 사유를 적지,
난수를 그리지 않는다. 챗봇에도 같은 자리를 만들어 둔 것이 `verify.py` 다.

그래서 지켜야 할 규칙이 셋이다.

1. **`TraceLog` 는 도구 결과를 원본 그대로 들고 있어야 한다.**
   요약해서 저장하면 대조할 것이 없어지고, 검증은 그냥 통과 도장이 된다.
2. **블록은 궤적에서 만든다. 답변 문장에서 만들지 않는다.**
   문장을 파싱해 블록을 만들면 모델이 지어낸 말이 그대로 막대그래프가 된다.
   숫자를 검증하는 층을 두고서 그 옆으로 지어낸 값이 그림이 되어 새어 나가는 셈이다.
   (`agent_path._terms_from()` 과 `agent_blocks.build()` 가 같은 이유로 궤적만 읽는다)
3. **`may_say` 를 무시하지 마라.** 관측이 모자라 말하면 안 되는 축이다.

### ★ 프론트가 모르는 블록 타입은 조용히 사라진다

`chat_api.js` 의 `BLOCK` 에 있는 것만 그려진다 — `rank` `bars` `table` `kpis`
`quotes` `prose` `links` `note` `upsell`. 모르는 `type` 은 **에러 없이 안 그려진다.**
`metric_chart` 같은 걸 새로 지어 쓰면 원인 없는 빈 칸이 된다. 새 블록이 필요하면
`blocks.py` 와 `chat_api.js` 를 **같이** 고쳐야 한다.

### ★ `as_of` 는 문자열이 아니라 객체다

`chat_api.reportHTML` 이 `rep.as_of && rep.as_of.metric` 으로 읽는다.
문자열을 주면 `.metric` 이 `undefined` 라 카드의 기준일이 **조용히 사라진다.**
한 번 당했다.

### ★ 근거 링크 — 없으면 없는 채로 내보낸다

`store.evidence_link()` 는 되돌아갈 수 있는 주소만 만든다.

| 플랫폼 | `product_uid` | 링크 |
| --- | --- | --- |
| 유튜브 | `yt:<video_id>` | `youtube.com/watch?v=...` |
| 무신사 | 숫자 상품 id | `musinsa.com/products/...` |
| 네이버 | `kw:<검색어>` | **불가능** — 글이 아니라 검색어다 |

실측(2026-09-09, 근거 454건): **308건(67%) 링크 가능.**

여기서 "네이버 블로그 검색 결과" 같은 그럴듯한 주소를 지어 붙이면, 누른 사람은
우리가 인용한 글이 **아닌** 곳에 떨어진다. 틀린 숫자와 같은 종류의 거짓말이다.
`url` 이 없으면 `None` 인 채로 내보내고, 답변에는 `(원문 링크 없음)` 이라고 적는다.
`orchestrator.INSTRUCTIONS` 6번 규칙이 그것이다.

### ★ RDS 로 갈아탈 때 손댈 곳은 `store.py` 하나다

지금 지표는 로컬 SQLite(`feedit-crawler/data/feedit.db`)에서 읽는다.
DB팀의 전처리가 끝나면 AWS RDS 로 옮긴다. 그때 고칠 함수는 셋뿐이다.

```
store.evidence_link()    플랫폼별 원문 주소 규칙
store.platform_label()   source_code · doc_kind → 한글 이름
store.at_iso()           시점 표기 통일 (RDS 는 timestamp 라 그냥 통과)
```

**위쪽(tools · orchestrator · blocks)은 건드리지 않는다.** 그러라고 이 경계를 만들었다.
(`at_iso` 가 왜 있냐면 — 네이버만 `20260902`, 나머지는 `2026-09-08` 로 와서
한 답변 안에 두 표기가 섞였다. 사람은 앞엣것을 숫자로 읽는다.)

### ★ 날짜를 숫자로 세지 마라

`verify.py` 가 답변의 숫자를 뽑아 도구 결과와 대조하는데, `2026-09-08` 을 그냥
숫자로 뽑으면 `-09` `-08` 이 **"지어낸 음수"** 로 잡힌다. 기준일을 성실히 밝힌
답변일수록 더 많이 걸리는, 정확히 거꾸로 된 판정이었다. `_DATE` 정규식으로
날짜를 **먼저** 걷어낸 뒤에 숫자를 뽑는다. 이 순서를 바꾸지 마라.

## 7. 환경변수

새 경로가 읽는 것 전부.

| 이름 | 기본값 | 뜻 |
| --- | --- | --- |
| `FEEDIT_CHAT_ORCHESTRATOR` | (꺼짐) | `1` 이면 새 경로 |
| `OPENAI_API_KEY` | — | 필수 |
| `FEEDIT_LLM_MODEL_LARGE` | `gpt-5.6-sol` | 아직 어느 역할도 안 쓴다 |
| `FEEDIT_LLM_MODEL_MID` | `gpt-5.6-terra` | 오케스트레이터 · 해석 · 조언 |
| `FEEDIT_LLM_MODEL_SMALL` | `gpt-5.6-luna` | 검증 · 발췌 · 다듬기 · 되묻기 |
| `FEEDIT_TOOL_WEB_SEARCH` | (꺼짐) | 호스티드 웹검색 |
| `FEEDIT_MCP_SERVERS` | (없음) | MCP 서버 JSON 배열 |
| `FEEDIT_LLM_DISABLED` | (꺼짐) | 모델 호출을 막는다 (테스트용) |

**모델을 왜 이렇게 나눴나** — 큰 모델을 다 쓰면 비싸고, 작은 모델을 다 쓰면
판단이 무너진다. 기준은 **"이 자리가 만들어 내는 일인가, 맞춰 보는 일인가"** 다.
검증은 창작이 아니라 일치 확인이고 출력이 스키마로 닫혀 있어서, 큰 모델로 올려도
얻는 게 거의 없다. 판단을 만들어야 하는 자리는 L1·L2 다.
`luna` 가 `terra` 보다 **기능이 적은 게 아니라** 깊이와 값이 다를 뿐이라,
작은 모델을 놓은 자리도 성능 저하가 아니다.

### ★ 제일 먼저 알아야 할 것 — 사전이 아직 관문이었다

| fit · color · tpo | 36 |

`search_terms` 가 사전만 보므로 브랜드는 **하나도 못 찾는다.** 아디다스도,
키르시도, 살로몬도. 그래서 "살로몬 XT-6 지금 사도 돼?" 에 이렇게 답했다.

> 아직 측정 자료가 없습니다.

**틀린 답이다.** 살로몬은 지표 표에 8행 있다. 온도 42°, 표본 7건, 기준일 09-02.
지어내지 않는 것과 있는 걸 못 보는 것은 다르다. 후자가 더 나쁘다 — 사용자는
우리가 확인했다고 믿는다.

고친 방식은 사전을 바꾸는 게 아니라 **뒷길을 낸 것**이다. 사전에서 못 찾으면
지표 표를 직접 본다.

```
store.metric_terms_in(text)   질문 안에 지표 표의 이름이 있나
store.metric_facet(canonical) 사전에 없는 용어의 축
Toolbox._key(term)            gate.facet_of → 없으면 store.metric_facet
```

`gate.term_key()` 는 `lex.facet_of` 만 보므로 브랜드는 `"None:살로몬"` 이 된다.
그래서 `_key()` 를 따로 뒀다. **사전 밖 용어를 다룰 때는 이쪽을 쓴다.**

찾았을 때 응답에 `source: "metric"` 이 붙는다 — 사전이 아니라 지표에서 찾았다는
뜻이다. 모델이 답변에 그 사실을 적을 수 있어야 한다.

**★ `term_key` 를 만드는 곳이 두 군데다.** `tools.Toolbox._key()` 를 고치고
`agent_blocks` 를 빠뜨렸더니, 지표 조회는 되는데 **카드만 비는** 상태가 됐다.
`report.build_term` 이 `"None:살로몬"` 으로는 못 찾아 `available=False` 가 되고,
블록 생성은 예외를 삼키므로(`블록은 덤이다`) 조용히 사라진다.
`agent_blocks._key_for()` 가 같은 규칙을 쓴다. **사전 밖 용어를 다루는 코드를
새로 쓸 때는 이 둘을 같이 보라.**

> **혁진에게 확인할 것** — 사전이 브랜드를 뺀 건 트렌드 순위가 홍보판이 되는
> 걸 막기 위해서였는데, 그건 아래 `TREND_FACETS` 로 따로 막았다. 사전이
> 브랜드를 몰라서 **조회까지 막는 것**은 원래 의도가 아니었을 것 같다.

### ★ 검증관이 맞는 숫자를 지우고 있었다

`verify.py` 의 오탐 다섯 계열. 공통점이 하나 있다 —
**답변이 성실할수록 더 많이 걸렸다.**

| 계열 | 무슨 일이 | 왜 |
| --- | --- | --- |
| 날짜 | `54.46 - 7일 평균` 의 `46 - 7일` 을 날짜로 먹어 `54.46` 이 `54` 로 잘렸다 | `_DATE` 두 번째 갈래가 구분자에 `-` 를 허용하고 공백까지 받았다 |
| 반올림 | 도구가 `54.46` 을 주고 모델이 `54.5` 로 적으면 지어낸 것으로 잡혔다 | 문자열 정확 일치로 대조했다 |
| 부호 | `delta_1w=-31` 을 "31° 하락" 으로 쓰면 대조 실패 — **실제로 지웠다** | `_numstr(-31.0)` 은 `"-31"` 이다 |
| 관측 창 | "7일 관측 3건, 14일 4건, 28일 4건" 의 14·28 이 잡혔다 | 값은 결과에 있지만 창 크기는 **키 이름**에만 있다 |
| 표 순번 | 순위를 표로 쓰면 `\| 1 \|` `\| 2 \|` 가 전부 잡혔다 | `_ORDINAL` 은 `"1. 자켓"` 꼴만 본다 |

4장의 함정 "날짜를 숫자로 세지 마라" 가 만든 **반대 방향 오탐**이 첫 번째다.
같은 함정이 방향만 바꿔 다시 나타난 셈이라, 이 파일을 고칠 때는 항상
**멀쩡한 답변으로 회귀를 돌려 보는 게 좋다.**

그리고 하나 더 — **도구를 하나도 안 부른 답변은 대조할 원본이 없다.**
`known` 이 빈 집합이라 모든 숫자가 의심으로 잡히고 `fix()` 가 전부 지운다.
호스티드 `web_search` 는 우리 `TraceLog` 에 안 남으므로("모델 쪽에서 돈다")
날씨 답변이 이렇게 나갔다.

```
오늘 서울은 맑고 약 °C 입니다. 밤사이 ~°C 로 선선하고, 낮 °C 안팎까지…
```

**확인할 원본이 없는 것을 지우는 것은 검증이 아니라 훼손이다.** 지우지 않고
`skipped=no_tool_results` 로 남기고, 화면에는 `WEB_SOURCED` 안내를 띄운다.

> 이 가드는 검증을 그만큼 느슨하게 만든다. 도구 없이 모델이 숫자를 지어내면
> 이제 안 걸린다. 규칙 1 이 그걸 금지하고 있고 사용자에게 안내가 나가지만,
> **우리 지표로 답한 경우만 엄격하다**는 것은 알고 있어야 한다.

`web_sourced` 판정을 처음엔 `res.sources` 로 했다가 틀렸다 — 호스티드 검색은
annotation 을 안 남길 때가 있어 `sources` 가 비면 가드가 통째로 무력해진다.
**판정 기준은 출처 유무가 아니라 "우리 도구를 불렀는가" 다.**

### 화면 — 서버는 보내고 있었는데 프론트가 버렸다

`server.py` 는 도구를 부를 때마다 `push("status", {stage:"tool", message})` 를
보내고 있었다. 그런데 `chat_popup.js` 의 핸들러 목록이
`text · report · actions · error · done` 뿐이라 **`askStream` 이 `on[ev]` 를 못
찾고 조용히 넘어갔다.** 4장의 "프론트가 모르는 블록 타입은 조용히 사라진다" 가
**이벤트 층에서 똑같이** 벌어지고 있었다.

`status` 핸들러를 붙였다. 전체를 다시 그리지 않고 **글자만 바꾼다** —
다시 그리면 별 회전 애니메이션이 끊긴다.

`b_direction` 의 `7일 / 4주` 칸도 고쳤다. `note` 가 늘 "1보다 크면 오르는 중"
이고 `up` 이 `ratio >= 1` 이라, `coverage` 가 **평평함**(0.9~1.1)이라고 판정한
1.03 이 바로 옆 칸에서 상승색으로 강조됐다. 본문은 "식은 상태" 라고 쓰고 있었다.
**문턱을 두 곳에서 따로 정하지 않는다** — `coverage.direction` 의 `tone` 하나만 본다.

### ★ 새 함정 — 로컬에서 목업만 나온다

**챗봇 서버는 떠 있는데 답만 목업**인 상태가 된다. 원인은 `.env` 의
`FEEDIT_CHAT_TOKEN` 이다.

```
/v1/health  →  _guard() 안 거침  →  200  →  isUp() 성공
/v1/chat    →  _guard() 거침     →  401  →  askStream 이 throw
                                          →  cpAsk 의 catch 가 cpAskMock 호출
```

`isUp()` 이 통과하니 "서버 없음" 으로도 안 보인다. 헷갈리기 딱 좋다.

`server.py` 주석대로 **로컬에서는 비워 둬야 한다** — "버셀 함수가 붙여 주므로
브라우저는 토큰을 모른다". `.env` 는 gitignore 라 이 함정이 코드에 안 남는다.
새로 받는 사람에게 꼭 말해 줄 것.

`FEEDIT_CHAT_TOKEN= python3 server.py` 로는 **안 된다.** `env.py` 가
`if override or not os.environ.get(k)` 로 채우는데 빈 문자열은 falsy 라
`.env` 값이 다시 덮어쓴다. `.env` 에서 줄을 주석 처리해야 한다.

**배포에서는 반드시 켤 것.** 없으면 주소만 알면 누구나 질문할 수 있고,
그건 곧 OpenAI 비용이다. 서버가 뜰 때 경고는 찍는다.

### 11.1 먼저 알아야 할 것

**① 예산의 뜻이 바뀌었다.**

> `FEEDIT_CHAT_TIME_BUDGET` 은 이제 **답변 하나의 전체 벽시계**다.
> (예전: 오케스트레이터 루프만.) 기본값 8 → 17 초. **권장 20~25 초.**
> `.env` 에 예전 뜻으로 적어 둔 값이 있으면 그대로 두지 말 것 — 루프가 굶는다.

나뉘는 방식은 이렇다. 예산 20 초 기준으로 **루프 12 · 마무리 6 · 검증 2**.

```
TAIL_RESERVE   8.0   루프는 마감시각보다 이만큼 먼저 멈춘다
VERIFY_RESERVE 2.0   그 8초 안에서 verify.fix 몫 (나머지 6초가 _finish)
WRITE_MIN      6.5   남은 시간이 이보다 적으면 새 바퀴를 시작하지 않는다
MIN_CALL       2.5   이보다 적게 남으면 아예 부르지 않는다
FINISH_MAX_TOKENS 700  마무리 답변 길이 상한
```

**② 새로 생긴 파일**

| 파일 | 무엇 |
| --- | --- |
| `AGENTS.md` | **고치기 전에 읽는 문서.** 증상을 덮지 말고 도구·스킬로 능력을 올린다 |
| `app/season.py` | 계절·기온 착용 기준표. 우리 지표가 아니라 **일반 기준**이다 |

**③ 로그 한 줄 읽는 법** (`server._log_turn`)

```
! [11:32:16] 18077ms stopped=llm_NET_ReadTimeout 바퀴=3(4173+2085+5756ms)
  웹검색=1 호출=4 도구=search_terms,get_metric,get_metric | https://…
```

`!` 는 정상이 아닌 줄이다. `stopped` 이 `llm_NET_ReadTimeout` 이면 **시간**,
`llm_HTTP_429` 면 **한도**다. 괄호 안은 바퀴별 소요, `웹검색` 은 호스티드 도구
호출 수 — 이건 우리 `TraceLog` 에 안 남으므로 여기서만 보인다.

### 11.2 남은 일 표에서 닫은 것

#### 17번 — 스펙이 축을 하나씩 받고 있었다

`declare_missing` 의 인자를 `axis: string` → `axes: array` 로. 없는 축이 몇 개든
한 번이면 된다.

가장 조심한 곳은 **저장 모양**이다. `trace.missing` 을 읽는 곳이 셋
(`verify.check` · `agent_path._notes` · `agent_blocks`)이라, 저장 모양까지 배열로
바꾸면 파급이 셋으로 퍼진다. 그래서 **기록은 예전 그대로 축 하나당 한 줄**로
쌓고 바뀐 것은 부르는 모양뿐이다. 세 곳은 한 줄도 안 고쳤다.

- 옛 모양(`axis` 하나)으로 불러도 받는다(`tools._axis_list`).
- `MAX_PER_TOOL` 상한은 **그대로 뒀다.** 고친 것은 스펙이고, 상한은 뒷문이다.
- 실측: "살로몬 XT-6" 이 `declare_missing` **1회**로 모멘텀·긍부정을 함께 기록.

#### 18번 — 예산은 지켰는데 답이 나빠졌다

`agent_path.ask()` 가 마감시각(deadline) 하나를 만들어 `orchestrator.run()` 과
`verify.verify()` 에 넘긴다. 루프 · `_finish` · `verify.fix` 가 그 하나를 나눠 쓴다.
남은 시간이 `MIN_CALL` 보다 적으면 **모델을 아예 부르지 않고** `STOP_SAY` ·
`_hedge` 가 받는다.

여기서 **두 번 헛디뎠고, 그 기록이 이 장에서 제일 쓸모 있다.**

| 뒷몫 | 예산 | 루프 몫 | 결과 |
| --- | --- | --- | --- |
| 9초 | 14초 | 7.0초 | **2/4 실패** — 루프 안에서 답을 못 만들고 안내문으로 끝났다 |
| 3.5초 | 17초 | 13.5초 | 4/4 done. **그런데 반대편이 굶었다** |
| **8초** | 20초 | 12.0초 | 지금 값. 마무리에 6초 |

3.5초 때는 `_finish` 몫이 1.75초라 `MIN_CALL` 에 못 미쳐 **아예 안 불렸다.**
링크 질문에서 카드는 끝까지 그려졌는데 본문만 안내문이었다 — 조회할 시간은
있었고 **문장 쓸 시간이 없었다.**

> **양쪽 실패를 같이 본다.** 너무 크면 답을 못 만들고, 너무 작으면 답을 못 쓴다.
> 하루에 둘 다 겪었다.

그리고 계측을 넣고서야 진짜 원인이 보였다.

```
! 18078ms stopped=llm_NET_ReadTimeout 바퀴=3(4751+3657+5563ms) 웹검색=1 호출=3
```

1·2바퀴가 조회(8.4초), **3바퀴째가 답을 쓰는 호출인데 5.6초에 잘렸다.** 그 뒤
`_finish` 도 4.0초를 받아 또 잘렸다. 한 번도 충분히 못 받고 두 번 실패한 것이다.
그래서 `WRITE_MIN` 을 4.0 → **6.5** 로 올렸다. **못 끝낼 호출을 시작하는 대신 그
시간을 마무리에 얹는다.** 같은 상황에서 마무리가 6초 → 11.7초를 받는다.

마무리 호출 자체도 가볍게 했다. 역할을 `orchestrator`(effort=medium)에서
**`finish`(luna · effort=low)** 로 바꾸고, 지시문을 `INSTRUCTIONS`(3,723자) 대신
`_FINISH_INSTRUCTIONS`(353자, 9%)로 줄였다 — 그 자리에서는 **도구를 고르지
않는다.** 출력도 700 토큰으로 묶었다. **예산을 지켜도 쓰다가 끊기면 아무것도 안
남는다.**

진단용으로 `trace.over_budget` 이 있다. **true 면 그 자체가 버그다** — 어느 층이
마감시각 밖에서 모델을 부르고 있다는 뜻이다(정상 답변이 경고를 달지 않도록
`agent_path.OVER_GRACE_MS` 250ms 여유를 뒀다).

#### 15번 — 되묻기 예산은 프롬프트가 아니라 도구 목록으로 건다

예산은 **대화당 1회**(`ASK_BUDGET`). 다 쓰면 `specs_for()` 가 목록에서
`ask_user` 를 뺀다. 부를 수 없으면 못 부른다 — 프롬프트로 부탁하는 것과 달리
이건 지켜진다. 막기만 하면 모델이 멈추거나 지어내므로, 컨텍스트에
`[되묻기 예산 소진]` 으로 **대신 할 일**(기본값으로 답하고 가정을 밝힌 뒤
"아니면 말씀해 주세요")을 함께 준다.

**★ 함정.** 예산은 `intent == "agent.ask"` 인 턴을 세는데, **클라이언트가 보내는
history 에는 그 턴이 없다.** `chat_popup.js` 는 `report` 이벤트가 올 때만 턴을
남기는데 되묻기는 `kind="meta"` 라 `server.py` 가 `text` · `done` 만 보내기
때문이다(`server.py:394`). 그래서 `engine` 이 **서버 기억에서도 세어** 둘 중 큰
쪽을 쓴다(`ctx["asked_before"]`).

세션 기억은 절반만 했다. `[최근 본 용어]` 5개는 컨텍스트에 들어간다(새로 저장한
것은 없다 — history 의 각 턴이 이미 `terms` 를 들고 있었다). **살말 카드 이력 ·
마지막 본 상품은 14번 이후**다.

`agent_smoke.py` 는 이 예산을 덮지 않는다. 확인하려면 팝업에서 **새 대화**로
"이거 어때?" 를 두 번 물어야 한다.

### 11.3 목록 밖에서 드러난 여섯

#### ① `WEB_SOURCED` 안내가 한 번도 뜬 적이 없다

10장은 "화면에 `WEB_SOURCED` 안내를 띄운다" 고 적어 뒀는데, **띄우는 쪽이 다른
문자열을 보고 있었다.** `verify` 는 `"no_tool_results"` 를 남기는데
`agent_path._notes` 는 `== "web_sourced"` 를 봤다. 그래서 웹으로 답할 때마다
안내 대신 "사실 확인을 끝내지 못했습니다" 라는 경고가 나갔다 — 사용자에게는
"웹에서 찾았다" 가 아니라 **"이 답을 믿지 마라"** 로 읽힌다.

사유 문자열을 `verify.NO_TOOL_RESULTS` 한 곳에만 두었다. **같은 뜻을 두 곳에
손으로 적으면 언젠가 어긋난다** — `term_key` 를 두 군데서 만들다 카드가 비었던
것(10장)과 같은 종류다.

그리고 이 사유에는 **두 경우**가 섞여 있었다. 호스티드 웹 검색으로 답한 것과
**아무것도 안 보고** 답한 것. 뒤쪽에도 "웹에서 찾은 내용으로 답했습니다" 가
붙었다. 판정은 그대로 두고(조이면 날씨 온도가 다시 지워진다) **문구만** 갈랐다 —
`res.sources` 가 있으면 `WEB_SOURCED`, 없으면 `NO_LOOKUP`.

#### ② 화면이 `notes` 를 처음으로 읽는다

`agent_path._notes` 는 다섯 가지를 보내는데 `chat_api.reportHTML` 이 보는 것은
`as_of` · `intent` · `blocks` 뿐이었다. **못 한 것을 숨기지 않는다는 원칙이
서버에서 끝나고 화면 앞에서 멈춰 있었다.** 4장의 "프론트가 모르는 블록 타입은
조용히 사라진다" 가 이번엔 **payload 층**에서 벌어진 셈이다.

`chat_api.notesHTML()` 을 만들고 `chat_popup.js` 의 `report` 핸들러가 카드 다음에
붙인다. `NO_DATA` 는 뺀다 — `agent_blocks` 가 이미 카드 안에 그린다. 카드가
아니라 **말풍선 아래**에 붙인다(블록이 없는 답은 카드를 아예 안 그리므로).
다시 그릴 때도 같은 자리에 오도록 `aiMsg.cueHtml` 로 남긴다.

#### ③ 마크다운이 문법 그대로 보였다

`**온도:** 56°` 가 별표째로, 줄바꿈도 없이 한 줄로 흘렀다. `mdclean.py` 머리말은
(가) 화면 렌더 / (나) 서버에서 제거 중 **(나)를 택했다**고 적어 두었고, 이유는
"렌더하면 HTML 을 허용해야 하니 주입 경로가 열린다" 였다. 예전 경로는 한 줄
결론이라 지워도 잃을 것이 없었지만, 새 경로 답변은 목록과 강조가 있는 여러
문단이라 별표만 지우면 한 덩어리가 된다.

`mdclean.to_html()` 을 새로 뒀다. **렌더하되 이스케이프를 제일 앞에서 한다** —
모델이 `<script>` 를 써도 그때는 이미 글자고, 결과의 태그는 전부 이 함수가 만든
것이다. 화면 계약("서버는 안전한 HTML 만 보낸다")은 그대로고, 바뀐 것은 **무엇까지
살려 보내느냐**다. 되묻기 보기도 `<ul>` 로 나간다.

#### ④ 이어 갈 질문이 근거보다 먼저 나왔다

모델이 질문을 본문에 섞어 쓰면 말풍선에 그려져 **카드 위**에 뜬다. 사용자는
근거를 보기도 전에 질문부터 받는다. 모델이 마지막 줄에 `[다음] …` 으로 쓰게 하고
(규칙 11), `agent_path._split_followup` 이 떼어 `followup` 으로 보낸다. 화면 순서는
**카드 → 이어 갈 질문 → 안내 줄 → 버튼**이다.

**표식이 없으면 아무것도 하지 않는다** — 끝 문장을 휴리스틱으로 떼면 멀쩡한
결론이 잘려 나간다. 못 찾는 편이 잘못 자르는 것보다 낫다.

#### ⑤ 검증관이 품번을 지웠다

```
측정 자료에 없는 내용을 덜어냈습니다: P5069에서 도구 결과에 없는 숫자 5069를 제거했습니다.
```

`P5069` 는 품번이고 `5069` 는 **주장이 아니라 이름의 일부**다. "Y2K" 의 2,
"XT-6" 의 6, "KD7983" 도 같은 자리다. 10장의 날짜·표 순번과 같은 계열의 오탐이라
같은 방식으로 먼저 걷어낸다(`_MODELCODE`). 라틴 문자에 붙은 숫자만 지우므로
"56점 · 42건" 같은 우리 값은 그대로 센다.

그리고 **덜어낸 내역은 화면에서 내렸다.** 사용자가 할 수 있는 일이 없는 내부
사정이고, 덜어낸 뒤의 답변은 이미 맞는 답이다. 숨긴 것이 아니라 자리를 옮긴
것으로 `trace.verify.removed` 에 그대로 남는다. **화면에 남기는 안내는 사용자의
판단이 달라지는 것뿐이다** — 없는 축 · 웹으로 답함 · 조회를 못 끝냄.

#### ⑥ 링크 질문이 조회만 하다 끝났다

로그가 `search_terms` **3연속**을 보여 줬다. 링크 → "아디다스 트랙탑" → "트랙탑"
으로 나눠 가며 부른 것이다. 한 번 부를 때마다 모델 왕복이 한 바퀴씩 들어가니
바퀴 셋을 조회에만 썼다.

그런데 **그 3연속은 내가 부추긴 것**이다. `search_terms` 의 못 찾음 안내에
"구성 요소로 나눠 한 번 더 찾아보십시오" 를 넣었는데, 스펙이 `q` 하나만 받으니
모델은 나눈 만큼 따로따로 부를 수밖에 없었다.

> 17번과 같은 모양이다 — **스펙이 하나씩만 받으면 모델은 하나씩 부른다.**
> 프롬프트로 "한 번에 하라" 고 부탁하기 전에 **한 번에 받을 수 있게** 만든다.

`search_terms(q="아디다스 트랙탑", alts=["아디다스","트랙탑"])`. 후보를 순회하되
첫 성공에서 멈추지 않는다 — 브랜드와 아이템이 둘 다 잡혀야 '나란히 보기' 가
붙는다. 대신 찾았으면 `substituted` 와 함께 "무엇 대신 무엇을 봤는지 반드시
밝히라" 는 지시가 따라 나간다.

이어서 `get_metric` 이 세 바퀴에 흩어지길래 프롬프트에 "용어가 여럿이면 **같은
바퀴에 나란히** 불러라" 를 넣었다.

### 11.4 새 도구 둘

#### `season_fit` — 지금 입을 만한가

"지금 가을인데 이 옷 입을 만해?" 에 "계절·기온 적합도 자료는 아직 측정 자료가
없습니다" 라고만 답하고 있었다. 틀린 말은 아니다(수명주기는 아직 계산 못 한다).
그런데 사용자가 물은 것은 지표가 아니라 **상식**이다. 반팔이 11월에 맞느냐는
측정하지 않아도 답할 수 있고, 못 한다고만 말하는 챗봇은 쓸모가 없다.

기준은 `app/season.py` 의 표에 **눈에 보이게** 적어 두고 도구는 그 표만 읽는다.
모델에게 판단을 맡기지 않는 이유는 하나다 — 그 판단에는 대조할 원본이 없어서
결국 지어낸 숫자와 같은 자리에 서기 때문이다. 표를 고치면 답이 바뀐다.

```
트랙탑 17°C → 적합    10~24°C에 어울리는 편이라 17°C 에 맞습니다.
반팔   17°C → 애매    17°C 는 경계입니다. 겹쳐 입기나 시간대에 따라 갈립니다.
코트   17°C → 부적합  12°C 이하에서 입는 편이라 17°C 에는 덥습니다.
```

기온은 모델이 `web_search` 로 확인해 넣고, 모르면 계절 평균으로 잡되 무엇으로
잡았는지 함께 돌려준다. 응답에는 항상 `not_feedit_data` 가 붙고, 프롬프트가
"일반 착용 기준이라고 밝히고 **트렌드 지표와 한 문장에 섞지 마라**" 를 강제한다.
표에 없는 말은 `unknown` 으로 돌려주고 판단하지 않는다.

> ★ 우리 '온도' 는 트렌드 점수이고 날씨 '기온' 은 °C 다. **이름이 같다.**
> 한 답변에 둘이 같이 나오면 반드시 구분해서 써야 한다.

#### `similar_terms` — 비슷한 것

세 번 고쳤다. 그 과정이 곧 이 도구의 설계다.

**1차 — 연관어를 그대로 내보냈다. 틀렸다.** 반팔 티셔츠 링크에 "비슷한 것" 으로
팬츠·자켓이 나왔다. 연관어는 *함께 언급된* 말이라 대부분 **코디(보완재)** 다 —
같이 입는 것이지 대신 입는 것이 아니다.

**2차 — 2차 연관으로 바꿨다.** 같은 자리에 놓이는 말은 같은 것들과 함께
언급된다. 티셔츠와 맨투맨은 둘 다 팬츠·데님과 함께 나오고, 팬츠의 연관어는
반대로 상의들이다. 그래서 base 의 연관어 집합과 후보의 연관어 집합이 얼마나
겹치는지(자카드)로 고른다. 검증에서 긴팔 0.80 · 맨투맨 0.67 · 자켓 0.33 이 뽑히고
팬츠는 겹침이 0 이라 빠졌다.

**그런데 연관어 표를 세어 보니 얇았다.**

```
연관어 표 전체 : 1054
  item:팬츠      0개 : []
  item:티셔츠    3개 : ['긴팔(긴소매)', '자켓', '코튼']
  style:레이어드  0개 : []
```

용어 580개에 1054행이고 팬츠는 아예 0개다. 원리는 맞지만 **지금 데이터로는
대부분의 용어에서 계산할 것이 없다.**

축을 더 잘게 쪼갤 수 있나 찾아봤지만 **없다.**

- 지표의 축은 `style · material · item · brand` 넷뿐이고 `item` 안에 상의·하의·
  가방이 전부 들어 있다. 그래서 "팬츠의 같은 축" 에 자켓·백팩이 나온다.
- 사전이 들고 있는 것도 `version · surfaces · facet_of · trendable · 차단어` 뿐이다.

**3차 — 이름 계열을 근거로 더하고, 자리를 나눴다.**

한국어 패션 용어는 복합어의 **뒤쪽이 범주**인 경우가 많다. 포함 관계이거나 공통
꼬리가 2자 이상이면 같은 계열로 본다(`_family`).

```
팬츠(연관어 0개) → 와이드팬츠 · 조거팬츠 · 카고팬츠
                   자켓 · 백팩 · 맨투맨 · 반바지는 빠진다
```

완벽하지 않다. '자켓/재킷' 처럼 표기가 갈리면 못 잡고 '블레이저' 는 놓친다.
**놓치는 것은 괜찮고 틀리게 묶는 것이 문제**라 기준을 느슨하게 잡지 않았다.

근거의 순서는 **① 2차 연관 → ② 이름 계열 → ③ 못 찾음**이다. ③이면 `items` 를
**비우고** 축 상위 목록을 `alternatives` 라는 다른 이름으로 보낸다. 화면 제목도
"아이템 축에서 지금 높은 것" 으로 갈린다. 같은 그릇에 담고 "이건 비슷한 게
아닙니다" 라고 덧붙이는 방식은 모델이 그 말을 빠뜨리는 순간 무너진다.
**섞일 수 없는 모양으로 준다.**

기준(base) 고르기도 도구가 한다. `terms` 배열로 후보를 받아
`BASE_ORDER`(item → material → style → tpo → fit → color → brand) 로 고른다.
"…레이어드 와이드팬츠" 에서 모델이 **레이어드**(스타일)를 기준으로 넘겨
"레이어드와 비슷한 것: 스트릿웨어 · 캐주얼" 이 나온 적이 있다 — **어느 축을
기준으로 삼느냐가 답의 종류를 바꾼다.** 아이템·소재 축이 아니면 `caution` 이 붙는다.

> **사진은 못 붙였다.** `store.py` 어디에도 이미지 열이 없고, 무신사 상품 id 만으로
> 이미지 주소를 만들 수도 없다(만들면 그건 지어낸 링크다 — 4장). 도구 응답과
> 프롬프트 양쪽에 "용어 단위이고 사진은 없다" 를 못 박아 뒀다. **상품 단위 추천과
> 사진은 RDS 에 상품 표가 붙은 뒤의 일이다.**

### 11.5 문체와 화면

답이 나오기 시작하자 **답의 모양**이 문제로 올라왔다.

- 모든 답이 "결론적으로," 로 시작했다. 카드가 이미 숫자를 보여 주는데 본문까지
  보고서 문투면 같은 말을 두 번 듣는다. → **사람과 대화하듯. 머리말 없이 첫
  문장에서 바로 답한다.**
- 한 덩어리로 흐르던 문단 → 한 문단 2~3문장, 문단 사이 빈 줄, 항목이 둘 이상이면
  `- ` 글머리표. `mdclean.to_html` 이 그대로 문단과 목록으로 그린다.
- 이어 갈 질문(`.nextQ`)은 본문과 같은 16.5px, **표식(✧) 없이**. 각주가 아니라
  챗봇이 거는 말이라 기호가 붙으면 시스템 메시지처럼 읽힌다.
- 못 한 것 줄(`.cue`)은 11px. 읽으려 들면 읽히되 먼저 눈에 들어오지는 않는 크기.

### 11.6 오늘 배운 것

`AGENTS.md` 에 규칙으로 옮겨 뒀다. 고치기 전에 그 파일을 먼저 읽을 것.

1. **증상을 덮지 말고 능력을 올린다.** 판단 기준 하나 — *이 고침이 다음에 올
   다른 질문도 낫게 만드는가?* 아니라면 증상만 덮은 것이다.
2. **한 번에 받을 수 있게 만든다.** 바퀴 하나가 예산에서 제일 비싼 항목이다.
   스펙이 하나씩만 받으면 모델은 하나씩 부른다(`axes` · `alts` · 같은 바퀴).
3. **계측이 없으면 처방도 없다.** 예산을 올리는 처방을 두 번 냈다가 두 번 다
   빗나갔다. 정작 제일 큰 항목("답 쓰는 데 몇 초가 드는가")을 재고 있지 않았다.
4. **같은 뜻을 두 곳에 손으로 적지 않는다.** `no_tool_results` / `web_sourced`
   가 어긋나 안내가 통째로 사라졌다.
5. **섞일 수 없는 모양으로 준다.** 말로 "이건 다르다" 고 덧붙이는 방식은 모델이
   그 말을 빠뜨리면 무너진다(`items` / `alternatives` / `paired_with`).
6. **화면까지 확인한다.** 서버가 보내는 것과 화면이 그리는 것은 다르다.
